# 对话笔记：LLM 约束解码、状态机与结构化输出

> 范围说明：本记录只保存本轮对话中关于状态机、FSM/PDA、逐 token 约束解码、logit 屏蔽和供应商 API 能力边界的讨论；后续案例不在本记录范围内。

## 1. 状态机是什么

对话中形成的核心理解：

- 状态机根据“当前状态”和“新输入”，决定执行什么动作以及切换到哪个新状态。
- 可以写成：`当前状态 + 输入 → 动作 + 新状态`。
- 状态不是完整历史，而是为了判断下一步行为，对历史所做的最小化总结。
- 地铁闸机示例：
  - 锁定状态收到“刷卡”输入后进入已解锁状态；
  - 同样收到“推门”输入，锁定状态拒绝通行，已解锁状态允许通行并回到锁定状态。
- “有限状态机”的“有限”，表示系统只会在预先定义的有限个状态之间转移。

## 2. 状态机如何描述 JSON 生成

对于目标 JSON：

```json
{"name":"小明"}
```

生成过程可以抽象为：

1. 尚未开始；
2. 生成 `{` 后，进入对象并等待字段名；
3. 字段名生成中；
4. 字段名结束，等待冒号；
5. 等待字段值；
6. 字符串值生成中；
7. 等待对象结束；
8. 合法结束（接受状态）。

“当前状态：字段名已经结束，正在等待冒号”是便于人理解的描述。实际系统中，它通常只是解码器或解析器内部的状态编号、语法节点或解析栈，并不会作为一段中文提示发送给模型。

## 3. 约束解码如何约束模型

大模型每一步会为词表中的所有候选 token 计算 logit。普通解码会对这些 logits 做 Softmax，再采样或选择得分最高的 token。

约束解码在“模型计算 logits”和“选出下一个 token”之间插入一个确定性步骤：

1. 模型根据已有 token 计算完整词表的 logits；
2. 外部语法约束器根据当前解析状态计算合法 token 集合；
3. 将所有非法 token 的 logit 设为负无穷；
4. 对剩余 token 采样或取最大值；
5. 把选中的 token 加入上下文；
6. 约束器读取该 token，并更新自己的状态；
7. 重复以上步骤直到进入接受状态。

伪代码：

```python
state = grammar.start_state()

while not state.finished:
    logits = model.forward(generated_tokens)
    allowed_tokens = grammar.allowed_tokens(state)

    for token in vocabulary:
        if token not in allowed_tokens:
            logits[token] = float("-inf")

    next_token = sample(logits)
    generated_tokens.append(next_token)
    state = grammar.update(state, next_token)
```

因此，提示词和约束解码的本质不同：

- 提示词是在告诉模型“应该遵守规则”，非法 token 依然可以被选择；
- 约束解码直接令非法 token 的概率变为 0，模型无法选择它们。

约束器不替模型决定内容，只划定合法候选范围。模型仍在合法范围内，根据语义和概率选择具体内容。

## 4. 为什么约束器需要处理 token 而不只是字符

模型生成的基本单位是 token，不一定是单个字符。一个 token 可能是：

- 单个标点；
- 一个词；
- 多个字符组成的 JSON 片段。

因此，约束器通常需要检查：把某个 token 对应的字符或字节序列接到当前前缀后，能否沿语法规则合法推进。一个 token 内可能连续跨过多个语法状态。

## 5. FSM、PDA 与更一般的语法约束

- FSM（有限状态机）只维护有限的当前状态，适合有限、固定或可正则化表达的结构。
- PDA（下推自动机）在状态之外还维护一个栈，可以记录任意深度的括号或结构嵌套。
- 对 JSON 这类存在递归嵌套的结构，工程实现也可能使用 PDA、上下文无关文法（CFG）、增量解析器或它们的优化变体，并不一定真的把全部规则展开成一张简单 FSM。
- “状态机”仍可作为理解入口：约束器把已生成前缀压缩为足以判断下一步是否合法的解析状态。

## 6. JSON Schema 与约束解码

JSON Schema 可以声明：

- 对象、数组、字符串、整数等类型；
- 必填字段；
- 枚举值；
- 部分长度、模式和取值限制；
- 是否允许额外字段。

服务端可以把可支持的 Schema 子集编译为 grammar、FSM/PDA 或其他解析结构，在逐 token 解码时实施约束。

它通常能保证的是结构和类型，而不是事实语义。例如，它可以保证 `age` 是整数，却不能保证生成的年龄与真实世界一致。应区分：

1. JSON 语法是否合法；
2. 输出是否符合 Schema；
3. 字段内容在业务或事实层面是否正确。

前两项适合由结构化输出和校验器处理，第三项仍依赖模型能力、外部数据和业务验证。

## 7. 调用供应商 API 时的能力边界

若供应商只提供普通文本生成 API，完整的逐 token 推理循环运行在供应商服务器内部。客户端通常只能接收最终文本或流式 token，无法在每一步取得并修改 logits，再让同一次生成继续。因此客户端无法自行实现真正的硬约束解码。

即使 API 返回 logprobs，它通常也只是在事后展示模型曾经给候选 token 的分数，不代表客户端可以修改分数并继续服务端的 KV Cache 和采样过程。

如果供应商提供 Structured Outputs、JSON Schema、Grammar、Response Schema 等原生能力，则可以由客户端提交约束规则，由服务端在内部实施约束。不同供应商及不同模式的保证范围可能不同：

- JSON mode 可能只保证输出是合法 JSON；
- Schema-based Structured Outputs 才可能进一步保证字段和类型；
- Function/Tool Calling 是否严格受 Schema 约束，要以具体 API 的保证为准，不能只根据功能名称推断底层实现。

若 API 不支持硬约束，客户端可采用较弱的闭环：

```text
生成 → JSON 解析 → Schema 校验 → 失败时携带错误信息重试或修复
```

这属于生成后校验与纠错，不是逐 token 约束解码。

## 8. 一句话总结

约束解码不是不断把“当前状态”发给模型，而是由模型外部的解析器根据已生成前缀维护语法状态；模型算出 logits 后，解析器将非法 token 的 logits 屏蔽，再允许解码器从合法候选中选择下一个 token。
