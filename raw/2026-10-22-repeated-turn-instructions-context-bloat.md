# 每轮重复注入规则导致长会话上下文膨胀：排障记录

## 来源与范围

2026-10-22，用户发现生涯对话服务的单次模型请求 input token 达到约 50k。排查先读取本地源码，再从用户提供的 EAS 终端核验运行路径，最终由用户在缩容后的实例执行只读脚本，回传目标模型消息的 usage 和历史链统计。

本记录为当次对话整理的证据摘要，不是完整日志或网关请求抓包。保留聚合数字；不保存访问令牌、内网入口、学生身份、对话正文、会话 UUID 或个人邮箱。时间均为北京时间。

## 历史组成统计

脚本定位目标模型消息最早的记录，从其 parentUuid 回溯历史链，排除目标回复本身。用户文本按拼接分隔符归类，历史 assistant 的相同消息 ID、块类型和块正文组合去重。以下为字符数，不是 token 数，也不是下游模型请求体的完整还原。

| 内容 | 请求 A 段数 | A 字符数 | 请求 B 段数 | B 字符数 |
|---|---:|---:|---:|---:|
| 学生信息 | 37 | 1,184 | 74 | 2,368 |
| 交互协议 | 37 | 25,234 | 74 | 50,468 |
| 当前消息＋画像＋记忆＋回灌 | 37 | 13,341 | 74 | 23,600 |
| 回复检查 | 37 | 25,086 | 74 | 50,172 |
| 历史思考文本 | 29 | 20,019 | 63 | 43,897 |
| 历史模型正文 | 36 | 7,480 | 73 | 14,032 |

交互协议每轮 682 字符，回复检查每轮 678 字符，合计每轮 1,360 字符。两项在 A 中累计 50,320 字符，在 B 中累计 100,640 字符。它们是服务端添加的文本，不是学生原话。

A 到 B 的单次 input_tokens 增加 44,639，除以新增的 37 条用户消息，平均约 1,206 token/轮。这是这段会话的观测斜率，不是可推广的固定增长率，也不能把全部增量都归给这两段规则。

## 源码与运行方式

项目 `ai-framework-template-career` 的 `app/biz/career/pooled_runner.py` 中，`build_pool_turn_prompt()` 为每轮拼接：学生信息、交互协议、task，以及从主 Skill 末尾复制的“发出回复前”检查项。拼好的文本通过 `client.query(task)` 加入常驻 CC 会话；后续轮继续携带历史。

- 主 Skill 作为静态 system prompt 绑定；不是每轮再向历史追加整份主 Skill。
- 固定交互规则与回复检查被混入 user message，随历史逐轮累积，没有在该拼接路径做历史去重。
- 线上观察到模型为 `deepseek-v4-1-flash-261017`，`--tools` 为空，`--max-turns=1`，`CAREER_USE_DIRECT=0`。
- 当次核查的 Claude 自动压缩窗口配置为 131,072；这不是实际触发阈值的精确证明。两个目标历史链均未发现压缩边界。
- 直连路径的 6,000 字符历史预算不作用于当前池化路径。
- 当前常驻池省的是进程启动和进程间续接开销，不能据此推断模型只接收最新一句话。

## 交互卡片边界与未决事项

本地代码中，完整测评卡片 JSON、题目与选项在模型输出后由后端生成并派发前端，不会在派发时自动整包进入 CC 上下文。交互协议、前端回传的 text、后端测评结果，以及模型生成的总结文字会进入对话路径。

回灌代码注释称计算结果“替代”原始答案，但实际在已有 cc_task 前追加 scored.resultText，已有回传文本仍保留。若 text 包含作答明细，可能同时输入答案与计算结果；目标会话未进一步拆分此项，不能量化其贡献。

JSONL 中记录了历史思考文本，尚未核验 SDK/网关是否在后续请求中原样保留、转换或过滤；不能把历史思考字符数直接计为已确认的输入 token。缓存统计为零也只代表本次返回的 usage，不可推广为平台永久不支持缓存。

用户说明服务曾扩容为 8 个 Pod，随后缩为 1 个。扩容不等于单次输入乘以 8；它影响记录定位、会话映射和恢复，需要独立排查。此次记录没有证明存在跨 Pod 重复恢复。

## 当次结论与状态

已确认：同一会话存在大量重复的交互协议和回复检查，目标历史链未压缩，单次输入从 53,679 增至 98,318。固定提示词混入追加式历史是明确的膨胀来源；各组成部分的精确 token 占比仍需核验下游请求体。

提出的改进是固定规则单份注入、当前轮检查不永久累积、画像/记忆有预算且可替换、历史压缩与恢复由 runtime 统一治理，并验收长会话输入增长。**本次仅完成排障与知识记录，未实施或部署修复，未测得修复后的节省比例。**
