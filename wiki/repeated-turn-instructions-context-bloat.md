# 每轮重复注入规则导致上下文膨胀

固定规则混入每轮追加的 user message，会从“本轮提示”变成反复重放的历史。短轮次可能看不出问题，长会话会让业务输入被规则副本挤占。不能只看 Skill 文件长度，也不能把常驻进程的增量续接等同于模型只处理增量输入。[来源：排障记录](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md)

## 已确认的案例

2026-10-22 的同一生涯会话中，两个模型请求分别记录 53,679 和 98,318 input tokens。历史链含 37 和 74 条用户消息，无缺失父记录、无压缩边界；交互协议和回复检查分别重复了 37 和 74 次，合计 50,320 和 100,640 字符。历史模型正文仅为 7,480 和 14,032 字符。[来源](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md#历史组成统计)

主 Skill 只作为 system prompt 绑定一份。每轮新增的是 682 字符交互协议和 678 字符回复检查，另有学生信息、画像、记忆和当前输入。两版主 Skill 只差 997 字符，因此主要调查对象是历史的组成和生命周期，而不是把 50k 归因于某版 Skill 太长。[来源](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md#版本与引入点)

## 机制与成本

假设每轮无条件追加长度为 s 的固定规则，所有历史均保留到第 n 轮，则该轮规则副本长度为 n×s；前 N 轮累计处理的规则长度为 s×N×(N+1)/2。单次上下文中的这部分线性增长，跨请求累计重复处理量二次增长。这是无裁剪条件下的结构推导，不是账单估计；缓存、分词、压缩与网关实现会改变实际计算和费用。[依据](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md#源码与运行方式)

把规则放入 system 也不意味着它只在整个会话中传一次；目标是在每次有效上下文中保留一份，而不是保留随轮数增长的多份。[设计建议依据](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md#当次结论与状态)

## 排查顺序

1. 区分单次请求、模型消息、业务轮次、Trace 和整个会话累计；按模型消息 ID 去重 usage，不能把同一消息的分块记录重复计数。
2. 定位目标回复，从其父记录回溯实际历史链，排除目标回复和之后的消息；检查压缩边界、分支和缺失父记录，不能简单汇总整个 JSONL。
3. 将静态 system、每轮规则、用户原文、画像、召回记忆、工具结果、历史回复分别统计。字符数只用于内容分布，不冒充精确 token 数。
4. 核验当时部署版本、挂载文件、运行中进程缓存和恢复历史；当前文件不证明历史请求用的版本。
5. 精确归因需要模型请求边界的观测：只记录必要的块类型、长度、指纹、token/缓存指标和版本，避免默认收集敏感正文。

这些步骤来自本次真实排障与其未决项；SDK/网关可能变换历史思考或工具块，持久化记录不一定等于最终请求体。[来源](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md)

## 设计与验收建议

以下是从案例推导的改进原则，尚非该服务已完成的修复：[来源](../raw/2026-10-22-repeated-turn-instructions-context-bloat.md#当次结论与状态)

| 内容 | 建议的生命周期 |
|---|---|
| 稳定规则、交互格式 | 统一放入每次有效上下文的一份系统规则中 |
| 当轮工具可用性、状态 | 以当前值替换或注入变化；旧状态必要时作为带时间的事件保留，避免与当前能力冲突 |
| 当前轮回复检查 | 若确需末尾强化，使用可重建的当轮提示；不作为用户原话永久追加 |
| 画像、召回记忆 | 有来源、版本与预算；只保留当前相关内容，并尊重用户纠错 |
| 对话与工具结果 | 按业务语义保留、摘要或裁剪，不按整块字符串相同就删除真实用户重复表达 |

上下文构建、压缩和恢复应由 runtime 统一管理。接入 SDK 时先核验可用的历史编辑/重建能力；若不支持，应设计有验证的会话迁移或受控重建，不能直接篡改正在使用的 JSONL，也不能为省 token 丢失用户纠错、交互状态和必要的工具调用配对。

验收覆盖短会话、长会话、压缩后续聊与恢复：固定规则副本数应保持有界，输入增长应由新增业务信息解释；交互启停、明确同意、回灌承接和用户纠错仍须正确。压缩窗口配置不是预算治理本身，也不能当成精确触发阈值。

## 不应得出的结论

- 不能把历史中的全部思考文本直接认定为已计入下一次输入；需要请求边界证据。
- 不能把前端卡片 JSON 与模型可见的交互协议、回传结果混为一谈。
- 不能把 Pod 数量当作单次 input token 的倍率。
- 不能把较短 Skill、命中缓存或接口成功当作长会话上下文治理已经通过验收。
